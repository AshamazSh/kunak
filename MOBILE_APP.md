# Кунак — единое мобильное приложение

Решение владельца: 16 октября 2026 года. Статус: требования согласованы; мобильные приложения, общий парольный вход API и публичная регистрация ещё не реализованы. Документ уточняет [PRODUCT.md](PRODUCT.md) и заменяет прежнее решение об отдельных покупательском и управленческом приложениях.

## Платформы и аудитория

На каждой платформе выпускается одно приложение «Кунак»: iOS на Swift + SwiftUI, Android на Kotlin + Jetpack Compose. Существующие репозитории kunak-ios-app и kunak-android-app содержат покупательскую и рабочую части. Отдельное приложение управления и новые репозитории для него не нужны.

Приложение предназначено для покупателей, сотрудников, администраторов бизнеса и глав франшиз. После авторизации открывается интерфейс соответствующей роли. Веб-кабинет администраторов и глав франшиз сохраняется. Состав и каналы экранов супер-администратора остаются отдельным открытым вопросом.

Один аккаунт имеет одну роль; объединение приложений не означает совмещения ролей или расширения прав. Сервер проверяет роль, разрешённое действие, бизнес, франшизу и точку при каждом защищённом запросе.

## Единый вход

- Один экран с email (логином) и паролем, без выбора «покупатель / бизнес» и без выбора роли.
- Сервер проверяет учётные данные и возвращает роль аккаунта; приложение открывает соответствующий интерфейс. Клиент не определяет права самостоятельно по введённому email.
- Покупательский вход по email и паролю сохраняется наряду с Google / Apple после настройки провайдеров. Провайдерский вход не выдаёт бизнес-роли; автоматического связывания по совпадению email нет.
- Существующие ограничения сессий, активности аккаунта и обязательной смены временного пароля управления сохраняются. При смене аккаунта нельзя показывать данные прежнего пользователя.

Покупателю доступны QR, баллы, штамповые карточки, условия скидок, собственная история, каталог/карта точек и профиль. Сотруднику доступны рабочие действия только в разрешённых точках; администраторам и главам франшиз — функции в пределах их роли. Детальный состав экранов ещё предстоит определить. Бронирования, альтернативы и связанные push остаются отложенными.

## Открытая регистрация покупателей

На экране входа доступен переход к регистрации по email и паролю. На первом этапе регистрация открытая, без приглашения и подтверждения email. Она создаёт только аккаунт customer без бизнес-привязки и управленческих разрешений. Супер-администратор сохраняет возможность создавать покупателей административным способом.

Email-логин нормализуется по существующим правилам и остаётся глобально уникальным, включая аккаунты управления. Регистрация не изменяет существующий аккаунт, его роль или пароль и не связывает провайдерские идентичности. Применяются существующие требования к новым паролям; имя и телефон остаются необязательными.

Подтверждение email одноразовым кодом добавляется позже. Это подтверждение владения адресом, а не согласованная замена входа по постоянному паролю. До внедрения подтверждения адрес нельзя считать проверенным. Самостоятельное восстановление/изменение покупательского пароля этим решением не добавляется; текущая смена через супер-администратора сохраняется.

## Подключение бизнеса

Внизу экрана входа располагается кнопка «Подключить ваш бизнес». Она ведёт на лендинг с формой подключения. Лендинг и форма будут разработаны позже; URL ещё не выбран. До появления страницы нельзя считать переход реализованным или подставлять вымышленный адрес.

Форма предназначена для заявки на подключение, а не публичного создания бизнес-аккаунта. Правила создания бизнеса, команды, назначения ролей и разрешений сохраняются.

## Затронутые направления и состояние API

- iOS и Android: общий экран входа, регистрация покупателя, переход к будущему лендингу и интерфейсы по роли в одном приложении каждой платформы.
- API: требуется общий серверный сценарий парольного входа для покупателей и управления, возвращающий существующий публичный user с role, и публичная регистрация только покупателей.
- Веб: лендинг с формой подключения — отдельная будущая задача; текущий кабинет не меняется этим обновлением документации.

Сейчас API использует отдельные POST /v1/auth/customer/password/login и POST /v1/auth/business/login; публичного маршрута регистрации нет. Один экран нельзя интегрировать путём публичного поиска роли по email или последовательного перебора этих входов. Конкретные маршруты/схемы общего входа и регистрации, поведение сессии после регистрации и совместимость существующих клиентов необходимо определить перед реализацией в [AUTH_CONTRACT.md](kunak-api/AUTH_CONTRACT.md). Этот документ не объявляет новые эндпоинты существующими.

Открыты также минимальные версии ОС, офлайн-поведение, подробная навигация и URL лендинга.
