# Кунак — инструкции для ИИ-агентов

## Запуск тестов — только по прямой команде владельца

- Запрещено запускать любые тесты без прямой команды владельца проекта на их запуск: обычные, интеграционные, сквозные, HTTP, браузерные, нагрузочные и тесты мобильных приложений.
- Запрет действует и на косвенный запуск через составные команды (например, `npm run check` или `npm run verify:mvp`), сборочные задачи, хуки, скрипты и автоматический запуск при изменении файлов, если они выполняют тесты. Перед запуском команды проверяй её состав.
- Просьбы разработать, исправить, продолжить работу или в общем проверить результат сами по себе не разрешают запуск тестов. Прежние указания об обязательных проверках не отменяют этот запрет.
- Проверку типов, линтер, форматирование и сборку можно выполнять без отдельной команды на тесты, только если они не запускают тесты.
- В результате явно сообщай, что тесты не запускались, если прямой команды на их запуск не было. Написание и изменение тестов само по себе не разрешает их запуск.

## О проекте

«Кунак» (Kunak) — платформа лояльности и бронирования для покупателей и бизнеса. Подключение — получение учётной записи от супер-администратора, заполнение данных и начало работы без интеграций с системами бизнеса. Состав MVP и открытые детали описаны в [PRODUCT.md](PRODUCT.md).

В пользовательских текстах и документации предпочтительно название «Кунак». `Kunak` / `kunak` используется там, где нужна латиница: идентификаторы, имена репозиториев, пакетов и технических ресурсов.

## Структура

- `kunak-api/` — бэкенд на TypeScript + Fastify; TypeBox для схем данных, OpenAPI для контракта API, PostgreSQL для хранения данных, Drizzle + `pg` + Drizzle Kit для запросов и миграций.
- `kunak-ios-app/` — нативное приложение iOS на Swift и SwiftUI.
- `kunak-android-app/` — нативное приложение Android на Kotlin и Jetpack Compose.

Каждая подпапка — отдельный Git-репозиторий со своим `AGENTS.md`. Корневая папка объединяет направления, но сама пока не является Git-репозиторием. Не выполняй Git-операции сразу для всех направлений без необходимости задачи.

## Ключевые требования MVP

- Покупатель: уникальный QR, история и состояние бонусов по бизнесам, карта подключённых точек, запросы на бронирование и выбор альтернативного времени.
- Бизнес: администратор, глава франшизы и сотрудник; отдельная глобальная роль — супер-администратор. Для покупателей согласована открытая регистрация по email и паролю, пока без подтверждения email; её API ещё не реализован. Создание покупателей супер-администратором сохраняется. Покупатели и бизнес-роли используют единое мобильное приложение с общим экраном входа; интерфейс определяется ролью аккаунта после проверки email и пароля сервером. Google / Apple предусмотрены для покупателей после настройки провайдеров. Пользователи управления используют email (логин) и пароль; учётные записи управления создаёт супер-администратор; администратор бизнеса может создавать business_admin, franchise_owner и employee своей сети, глава франшизы — franchise_owner и employee только своей франшизы. Изменение роли существующего аккаунта остаётся за супер-администратором. Совмещение ролей и работа сотрудника в нескольких независимых бизнесах не поддерживаются; несколько разрешённых точек своего бизнеса допустимы. Супер-администратор имеет доступ ко всем пользователям и записям, включая операции франшиз. Он действует в собственной глобальной роли. Администратор бизнеса создаёт команду своей сети и назначает сотрудникам точки и действия; глава франшизы создаёт команду и назначает действия только в своей франшизе. Роли существующих аккаунтов меняет супер-администратор.
- Лояльность: настраиваемые баллы, скидки и штампы. Сотрудник сканирует QR и начисляет штамп или вводит сумму покупки для расчёта баллов.
- Программы и условия лояльности можно настраивать отдельно по точкам: например, повышенное начисление в новой кофейне. Начисление рассчитывает сервер по программе точки; изменение условий не пересчитывает историю. Программы всех точек, включая франшизы, из бизнес-ролей задаёт только головной администратор; супер-администратор также имеет это право. Все бонусы действуют во всех точках одной сети независимо от принадлежности; разные условия начисления не ограничивают места использования.
- Франшиза ограничена своими точками; её операционные данные недоступны общему администратору, кроме данных конкретной операции для согласованной отмены начисления/списания. Баланс покупателя общий в пределах сети и используется в любой точке, включая франшизы. Из бизнес-ролей настройками управляет только администратор; супер-администратор имеет полный доступ. Глава франшизы просматривает статистику своих точек и управляет командой своей франшизы; настройки программ остаются за головным администратором и супер-администратором.
- Сотрудник выполняет только действия, разрешённые администратором своего бизнеса или супер-администратором для соответствующих точек.
- Бронирование: дата, время, количество человек; подтверждение, отказ, несколько альтернатив или звонок. Выбор альтернативы покупателем сразу подтверждает бронь.
- Покупатели, сотрудники, администраторы бизнеса и главы франшиз используют единое мобильное приложение на iOS и Android с интерфейсом по роли. Вход по email и паролю без выбора типа пользователя. Для администраторов и глав франшиз сохраняется веб-кабинет. Каналы интерфейса супер-администратора ещё уточняются. Решение о входе, регистрации и ссылке на подключение бизнеса — [MOBILE_APP.md](MOBILE_APP.md).
- Телефон и данные профиля необязательны; формат телефона российский, `+7` и десять цифр. Изменения брони приходят через push и видны в личном кабинете.
- В схеме данных отделяй область бонусов от программы начисления и точки; в MVP область — вся сеть. Отдельные области для франшиз допускаются будущей моделью, но не реализуются как режим MVP.
- Фото чеков — после MVP. Детальные открытые вопросы перечислены в `PRODUCT.md`.

## Уточнения первого этапа лояльности

Сначала реализуются баллы: настраиваемый процент от суммы покупки в копейках, целые баллы с округлением вниз за каждую покупку. Программа точки наследует основную и переопределяет отдельные поля, незаданные поля следуют её изменениям. Счёт общий по сети, включая франшизы. Штампы/скидки реализованы отдельными этапами API. Списание и отмена согласованы в следующем разделе. Прочие возвраты/ручные корректировки, сроки действия и права бизнес-ролей на общий баланс требуют отдельных решений; не выводи их из формулы начисления. Контракт — kunak-api/LOYALTY_POINTS.md.

## Уточнение списания и отмены баллов

Курс балла и лимит списания задаёт головной владелец сети. Начисление по действующей программе — от полной суммы покупки, включая часть оплаты баллами. Сотрудник списывает после QR/устного подтверждения, нужны scan_qr и redeem_loyalty в этой точке.

Головной владелец может отменять начисления и списания во всей своей сети, включая франшизы. Исключение из изоляции операций франшиз ограничено данными конкретной операции и её отменой; не открывает статистику или общую покупательскую историю. Супер-администратор сохраняет полный доступ. История сохраняется, отмена отдельной записью, отрицательный баланс запрещён.

Контракт — kunak-api/LOYALTY_REDEMPTION.md. Покупательская история теперь kind=accrual/redemption/reversal; не предполагай awardedPoints у всех записей. Покупка со списанием сама начисляет от полной суммы; не отправляй второе начисление с новым ключом. Штампы начисляются сотрудником по одному; реализация описана в контракте штампов ниже.

## Штамповые карточки

Несколько независимых карточек по наградам; счёт каждой общий во всей сети, включая франшизы. Баллы и штампы разных карточек не смешиваются. Сотрудник добавляет строго +1 после QR (scan_qr + accrue_loyalty); при выдаче одной награды с устным согласием (scan_qr + redeem_loyalty) списывает текущий порог точки, остаток сохраняется. Автоматических готовых наград нет. Новый порог применяется к следующей выдаче без пересчёта истории.

Настройки и отмена — головной владелец сети/супер-администратор. Как и для баллов, отмена конкретной операции франшизы не открывает общую статистику/историю. Контракт — kunak-api/LOYALTY_STAMPS.md. deltaStamps/balanceStamps — строки bigint; карточки различать по ID, не по названию. После начала использования rewardName не заменяется другой наградой: создаётся другая карточка. Скидки и сочетание механик реализованы по kunak-api/LOYALTY_DISCOUNTS.md в API; мобильные экраны ещё впереди.

## Фиксированные скидки и совместное начисление

Утверждено: фиксированный процент сети с nullable переопределениями точки; накопительные уровни позже. В одной покупке ровно один способ уменьшить цену: скидка либо списание баллов. Баллы начисляются от полной суммы до уменьшения цены; одновременно можно добавить +1 штамп одной выбранной карточки. Единый POST /v1/loyalty/locations/:locationId/purchases фиксирует всё атомарно с общим UUID-ключом сети; старые маршруты не должны добавлять отсутствующий бонус тем же ключом. Сотруднику для скидки нужны scan_qr + apply_discount, для начисления — accrue_loyalty; права не выдаются автоматически. Контракт — kunak-api/LOYALTY_DISCOUNTS.md. Покупка хранит исторический расчёт, деньги не принимает. Отмены бонусов отдельные; общий возврат покупки не реализован.

## Рабочий контекст после QR

POST /v1/loyalty/qr/context согласован и реализован: сотрудник с scan_qr своей точки получает текущие сетевые баллы/штамповые карточки и действующие условия точки, без покупательской истории/персональных данных. Super_admin имеет глобальный доступ; головной администратор/глава франшизы не получают права сотрудника. Чтение не создаёт счета/операции; bigint — строки, карточки постраничные. Старый resolve сохраняет только customerId. Единый ответ использует общий lock сети после актёра/точки/покупателя; следующий POST покупки заново проверяет права/условия/остаток. Контракт — kunak-api/LOYALTY_CONTEXT.md.

## Пароль покупателей — уточнение 14 октября 2026

В текущей версии постоянный пароль покупателя меняет только супер-администратор: PUT /v1/admin/customers/:id/password, currentPassword исполнителя и newPassword цели. Старая сессия покупателя отзывается на всех устройствах; изменение и аудит атомарны. Самостоятельной смены/восстановления, временного режима и автоматической рассылки покупателю нет. Отсутствующий парольный вход у провайдерской учётной записи этим методом не добавляется; отключённый аккаунт не включается. Правила собственной смены пароля пользователей управления сохраняются. Контракт — kunak-api/ACCOUNT_LIFECYCLE.md.

## Управление покупателями — 14 октября 2026

Супер-администратор с подтверждением собственного пароля включает/отключает customer через PUT /v1/admin/customers/:id/status и отзывает все его сессии через DELETE /v1/admin/customers/:id/sessions. Это применимо к парольным и провайдерским покупателям. Отключение сохраняет профиль/QR/идентичности/бонусы, запрещает вход и новые операции по QR. Включение не восстанавливает старые сессии. Изменение и аудит атомарны; физического удаления нет. Контракт — kunak-api/ACCOUNT_LIFECYCLE.md.

## Базовая статистика MVP

GET /v1/businesses/:businessId/statistics/loyalty: from/to обязательны, locationId необязателен; положительный период до 366 суток [from,to), явные UTC/смещения. Головному владельцу только franchise_id IS NULL, главе франшизы только его franchise_id, super_admin все точки выбранной сети; SQL-фильтр до агрегатов. Покупки/уникальные покупатели/суммы берутся только из loyalty_purchases, движение баллов/штампов/отмен — из журналов, без второго подсчёта автоматического начисления. Отмена учитывается на свою дату, не переписывает суммы покупок. Все агрегаты — десятичные строки, один снимок read-only REPEATABLE READ. Остатки карточек/сетевой баланс и личная история в статистику не входят. Миграция 0014 только индексы. Контракт — kunak-api/LOYALTY_STATISTICS.md.

## Редактирование конфигурации — 14 октября 2026

Головной администратор своей сети и супер-администратор могут читать GET /v1/businesses/:businessId и менять название бизнеса/франшизы/точки через PUT соответствующего ресурса. Только name; переносы точек/сетей не допускаются. Настройки адреса/публикации остаются отдельным каталогом. Переименование не пересчитывает бонусную историю и не раскрывает операции франшиз. Изменение и аудит атомарны; повтор неизменного названия не создаёт события. Контракт — kunak-api/MANAGEMENT_CONTRACT.md.

## Приёмка API MVP

В kunak-api Только по прямой команде владельца npm run verify:mvp запускает типы/Biome, обычные, интеграционные и сквозной HTTP-тесты; test:acceptance отдельно собирает и запускает dist/server.js во временной схеме PostgreSQL. ## Делегированная команда — 15 октября 2026

Учётные записи управления создаёт супер-администратор; администратор бизнеса может создавать business_admin, franchise_owner и employee своей сети, глава франшизы — franchise_owner и employee только своей франшизы. Изменение роли существующего аккаунта остаётся за супер-администратором. Глава франшизы также назначает своим сотрудникам точки и действия только внутри своей франшизы. Employee может иметь franchiseId; вне этой франшизы действие запрещено даже при наличии ошибочной строки разрешения. Создание не выдаёт разрешения автоматически; временный пароль требует смены. Глобальный список/карточки пользователей, управление активностью/паролями/сессиями и журналы остаются только super_admin. GET /v1/businesses/:businessId/team и списки сотрудников/точек фильтруются по области до пагинации. Миграция — kunak-api/drizzle/0016_delegated_team.sql; контракт — kunak-api/MANAGEMENT_CONTRACT.md.


## Штамповые программы: активность и сроки — 15 октября 2026

Основной isAccrualEnabled карточки — общий переключатель активности: отключение или срок вне startsOn/endsOn блокирует начисление и выдачу во всех точках; переопределение точки не обходит запрет. Даты включают последний день по Europe/Moscow, по умолчанию бессрочно. При повторном включении/возобновлении требуется явное решение restoreBonuses с expectedVersion. Отказ от восстановления помечает прежние счета только этой карточки is_valid=false без удаления; новые накопления отдельные. Баланс читает только действительные счета, история сохраняется с bonusesValid. Отмены невалидных бонусов не изменяют новый счёт. Миграция 0017, контракт — LOYALTY_STAMPS.md в API. Тесты без прямой команды владельца не запускать.

## Одноразовые штамповые карточки — 15 октября 2026

isOneTime=true ограничивает покупателя одной неотменённой наградой карточки во всей сети. Новое начисление +1 допускается только ниже текущего порога точки. После выдачи карточка завершена; отмена выдачи возвращает возможность получить награду. Старые остатки не удаляются. Выключение/возобновление и сброс накоплений не сбрасывают факт получения награды, включая выдачи старых невалидных счетов. Включение режима учитывает прежние выдачи; явное выключение режима возвращает многоразовое использование. Покупательские условия, счета и QR-контекст содержат isOneTime/isCompleted. Недоступная выбранная карточка отклоняет единую покупку целиком. Миграция 0018; контракт — LOYALTY_STAMPS.md в kunak-api. Тесты без прямой команды владельца не запускать.
