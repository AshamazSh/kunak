# Кунак — инструкции для ИИ-агентов

## О проекте

«Кунак» (Kunak) — платформа лояльности и бронирования для покупателей и бизнеса. Подключение — заполнение данных и начало работы без интеграций с системами бизнеса. Состав MVP и открытые детали описаны в [PRODUCT.md](PRODUCT.md).

В пользовательских текстах и документации предпочтительно название «Кунак». `Kunak` / `kunak` используется там, где нужна латиница: идентификаторы, имена репозиториев, пакетов и технических ресурсов.

## Структура

- `kunak-api/` — бэкенд на TypeScript + Fastify; TypeBox для схем данных, OpenAPI для контракта API, PostgreSQL для хранения данных, Drizzle + `pg` + Drizzle Kit для запросов и миграций.
- `kunak-ios-app/` — нативное приложение iOS на Swift и SwiftUI.
- `kunak-android-app/` — нативное приложение Android на Kotlin и Jetpack Compose.

Каждая подпапка — отдельный Git-репозиторий со своим `AGENTS.md`. Корневая папка объединяет направления, но сама пока не является Git-репозиторием. Не выполняй Git-операции сразу для всех направлений без необходимости задачи.

## Работа над проектом

- Общайся и веди проектную документацию на русском языке. Для идентификаторов в коде используй английский.
- Перед изменениями читай локальный `AGENTS.md` соответствующего направления и проверяй текущее состояние репозитория. Сохраняй чужие изменения.
- Отделяй утверждённые требования от предложений. Не представляй предполагаемые функции как уже согласованный продукт.
- Стек API зафиксирован в `kunak-api/AGENTS.md`. В MVP вход только Google / Apple; одноразовый пароль на email — после первого этапа. Минимальные версии ОС и оставшиеся инфраструктурные решения не представляй как установленный стандарт до обсуждения с владельцем проекта.
- На текущем этапе проект должен быть простым и легковесным. Большинство кода создаётся с помощью ИИ; предпочитай явные типы, короткие понятные функции и автоматические проверки сложным абстракциям.
- Стремись к простому решению задачи; не добавляй сервисы, зависимости и абстракции без конкретной потребности.
- При изменении взаимодействия приложений и API явно описывай контракт и затронутые направления. Не выдумывай существующие эндпоинты; временные данные и заглушки отмечай явно.
- Не храни секреты и персональные данные в коде, документации, тестовых примерах и логах.
- Выполняй доступные проверки, подходящие к изменению. В результате сообщай, что изменилось, что проверено и какие ограничения остались. Не заявляй об успешной сборке, если она не запускалась.

## Ключевые требования MVP

- Покупатель: уникальный QR, история и состояние бонусов по бизнесам, карта подключённых точек, запросы на бронирование и выбор альтернативного времени.
- Бизнес: администратор, франшиза и сотрудник; настройки программ, управление бонусами и сотрудниками, франшизы и статистика.
- Лояльность: настраиваемые баллы, скидки и штампы. Сотрудник сканирует QR и начисляет штамп или вводит сумму покупки для расчёта баллов.
- Программы и условия лояльности можно настраивать отдельно по точкам: например, повышенное начисление в новой кофейне. Начисление рассчитывает сервер по программе точки; изменение условий не пересчитывает историю. Программы всех точек, включая франшизы, задаёт только головной администратор. Все бонусы действуют во всех точках одной сети независимо от принадлежности; разные условия начисления не ограничивают места использования.
- Франшиза ограничена своими точками; её операционные данные недоступны общему администратору. Баланс покупателя общий в пределах сети и используется в любой точке, включая франшизы. Всеми настройками управляет только администратор. Франшиза только просматривает статистику своих точек.
- Сотрудник выполняет только действия, разрешённые администратором для соответствующих точек.
- Бронирование: дата, время, количество человек; подтверждение, отказ, несколько альтернатив или звонок. Выбор альтернативы покупателем сразу подтверждает бронь.
- Покупатели и сотрудники используют одно мобильное приложение по ролям. Администраторы и франшизы — веб-кабинет и отдельное приложение управления; его платформы, организация исходников и веб-стек пока не выбраны.
- Телефон и данные профиля необязательны; формат телефона российский, `+7` и десять цифр. Изменения брони приходят через push и видны в личном кабинете.
- В схеме данных отделяй область бонусов от программы начисления и точки; в MVP область — вся сеть. Отдельные области для франшиз допускаются будущей моделью, но не реализуются как режим MVP.
- Фото чеков — после MVP. Детальные открытые вопросы перечислены в `PRODUCT.md`.
